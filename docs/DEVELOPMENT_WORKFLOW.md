# Local → GitHub → Vercel workflow

Repository: `https://github.com/ShahZamanHaider/ROBETIX_CAM`. Production branch: `master` as observed during this audit. Authentication work is isolated on `feat/auth-recovery-sessions`, starting from checkpoint `checkpoint/pre-auth-workflow` (`8cf4a78`). No force push or automatic production merge is part of this workflow.

1. **Inspect and preserve:** `git status --short`, `git branch -avv`, `git remote -v`, `git fetch origin`. Review uncommitted changes. Create a source checkpoint before substantial changes. Keep account/data configuration separate from source; never recreate Supabase or Vercel projects to fix a login issue.
2. **Implement on a branch:** keep the existing firmware and `remote/` structure. Backend authentication needs no application SQL migration. Future database changes require a new numbered, non-destructive migration, isolated database testing, a backup and confirmed production application before deploying dependent code. A pushed SQL file is not an executed migration.
3. **Test:** run the commands in `remote/AUTHENTICATION.md`. `npm --prefix remote run build` generates the hosted bilingual bundle without altering firmware. PlatformIO's embed script also preserves that remote-only auth dictionary. Firmware-affecting changes additionally require `pio run`; compilation alone does not establish hardware behavior.
4. **Check secrets:** real local values belong only in ignored `remote/.env.local`. `remote/.env.example` contains placeholders and safe non-secret origin settings. Run `git check-ignore remote/.env.local` and `node tools/check-secrets.mjs --history`. The latter checks tracked/staged text, known local key matches, credential shapes and all referenced Git history without printing matched values. It is a practical check, not proof against every possible unknown secret representation. Investigate every finding before pushing.
5. **Stage and commit intentionally:** review `git diff`, stage the intended files, run `git diff --cached --check` and repeat the secret check, then commit verified work with a meaningful message. Use the repository's configured GitHub-verified author identity (`git config user.email`); an unrecognized generic author can block Vercel deployment. Never add `.env.local`, downloaded credentials, `.vercel` state, or build output. The user's previously uncommitted real example configuration was preserved in ignored `.env.local`; the example was restored to placeholders. None of those real values should be moved into history.
6. **Push the branch:** `git push -u origin feat/auth-recovery-sessions`. This does not merge it into `master`. If permissions fail, obtain only the necessary repository/workflow permission. Keep the source checkpoint and existing production deployment intact.
7. **Verify CI and Preview:** `remote-checks.yml` runs backend/auth, language, secret, PostgreSQL/WASM and browser checks using fake provider credentials. `firmware-checks.yml` compiles only when firmware/data/embed paths change. Jobs have read-only repository permissions and receive no production service secrets. These checks do not automatically block Vercel's Git integration; require successful checks and a reviewed Preview before manually merging to production. Set required status checks/branch protection in GitHub if enforcement is wanted; those administrator settings were not silently changed here.
8. **Verify the deployment:** `node tools/check-deployment.mjs` reads GitHub commit/deployment metadata using the existing Git credential helper or `GITHUB_TOKEN`. It never prints the credential. Confirm the Vercel result for the intended commit and open its actual URL. GET `/api/health` should report version 3 and the intended commit SHA; GET `/api/auth?action=session` without cookies should return `authenticated:false`; unauthenticated private APIs and reset POSTs must reject access. Recovery pages should load but cannot reset without a valid proof. Deployment success is separate from push and CI success.
9. **Production promotion:** only a human-approved merge/promotion updates production. Review Supabase URL/SMTP configuration and smoke-test recovery with a real authorized email first. Keep the existing production deployment available. On failure use Vercel's existing deployment rollback/promote workflow after checking account/project/target; Git source can be reverted with a new commit. Do not rewrite shared history, force-push, rotate unrelated secrets or change DNS as a shortcut.

The production URL supplied by the user is `https://robetixvision.vercel.app`. `vision.robetix.com` is a future verified alias; this work does not change the main website or portfolio DNS. Read-only audit confirmed production version 2 at the starting commit and rejected unauthenticated device listing. Release/CI outcomes are recorded separately after push, so older “not deployed” development notes remain historical evidence rather than current account-state claims.

Firmware upload is separate: Vercel does not flash the ESP32. The authentication release does not change capture/network C++ or add OTA. The included local Wi-Fi help copy needs an optional normal firmware upload to appear on the board. A future secure OTA design needs partition capacity, authenticated updates, signing/integrity, rollback and power-failure analysis; none was silently enabled.
