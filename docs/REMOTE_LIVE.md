# Remote live viewing and camera setup

## Implementation and activation status

Branch `feat/remote-live-setup` builds on the tested authentication branch. Production is not automatically changed. This implements the firmware, authenticated ticket API, consumer browser viewer, pairing protections and a deployable stateful relay. **Public end-to-end viewing is not yet verified:** the relay has not been deployed, migration 003 has not been applied to production, and no ESP32 is attached. Software simulations do not establish camera FPS, latency, power stability or SD coexistence.

## Transport

The ESP32's existing capture task supplies OV2640 native JPEG frames. It copies at most one 128 KiB image plus a 24-byte header into PSRAM using a nonblocking mutex; network I/O runs in the existing cloud worker, outside the camera lock. Slow SD writes (>50 ms in the last recording append) skip live copies. Manual/local viewing and recording retain their profiles. Otherwise Low uses QVGA/JPEG24/1 FPS ceiling; Normal VGA/JPEG20/2 FPS ceiling; Best SVGA/JPEG20/2 FPS ceiling. These are configured ceilings, **not measured performance**. Profiles restore when viewing ends. No PSRAM means remote frames are unavailable; local operation continues.

Verified outbound WSS reaches a Cloudflare Worker, routed by camera UUID to one SQLite Durable Object. At most one camera socket and two viewer sockets are accepted per camera. The relay forwards binary JPEG packets immediately without storing footage. Each viewer must acknowledge a decoded image before another frame is sent; slow viewers drop intervening frames and close after eight seconds without ACK. Capture times older than five seconds are rejected. Browser images are hidden after 4.5 seconds without a decoded new frame. No frozen image is labeled live.

`RVJ1` packet fields, big endian: magic[4], sequence uint32, width uint16, height uint16, JPEG length uint32, captured Unix milliseconds uint64, JPEG bytes. The firmware timestamp currently has one-second precision. Relay JPEG marker/dimension/length checks bound input; the browser actually decodes JPEG before ACK. There is no audio, transcoding or AVI playback in remote live view.

Vercel serves the website, sessions and short-lived authorization. Supabase retains accounts/device ownership/activity; it does not carry continuous video. Vercel now supports WebSockets, but separate connections can land in different instances and functions expire. The Durable Object provides explicit per-camera coordination and bounded buffering without adding a continuously running server. See [Vercel WebSockets](https://vercel.com/docs/functions/websockets) and [Cloudflare hibernating WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).

No frames upload while unwatched, although the camera keeps a lightweight relay connection when remote access is enabled. Tickets expire in 90 seconds. Camera heartbeat refreshes authorization every 60 seconds and temporarily closes its WSS connection; event-photo/WhatsApp HTTPS work takes priority over video and can cause gaps. Browser reconnects with fresh owner authorization after three seconds. Ticket/API failures retry after ten seconds. Switching the browser to the background pauses viewing; returning requires Resume. This is deliberately reduced-rate live video, not smooth guaranteed CCTV streaming.

The WSS client checks the TLS certificate and WebSocket accept proof, masks outgoing frames, bounds control messages to 512 bytes and limits frame-send work. An extra 128 KiB PSRAM slot and a 10 KiB cloud task stack are used. Public roots live in flash. TLS heap guards require 68 KiB total /32 KiB largest internal block before WSS connect; failed allocation does not take camera ownership. Actual peak heap and TLS handshake behavior require hardware testing.

## Security and ownership

Vercel signs one-use role/device/Origin-scoped HMAC tickets using server-only `LIVE_RELAY_SECRET`. Viewer tickets come only from authenticated owned-device checks; camera tickets require its existing hashed device credential and remote enabled. Tickets travel as a WebSocket subprotocol, not query strings, and remain in browser memory. Relay secret never enters browser or firmware. Nonces and expiry are enforced by the camera room, including across room hibernation. Disconnection rotates/disables device credentials and requests immediate live-session closure. If relay revocation is unreachable, already-issued tickets expire within 90 seconds; this is not instantaneous global logout.

Migration 003 adds a private hardware-claim registry and optional display name. A random factory hardware tag persists across the application's normal factory reset. Pairing uses a five-minute account code and physical access to the local administrator page. An active registered camera cannot be claimed again until its cloud owner disconnects it. Transfer creates a fresh device ID, leaving historical photos/recipients with the prior owner. Up to 20 active cameras per account are allowed (five tested in simulation). Already-paired upgraded firmware binds its factory tag on its next authenticated heartbeat when setup is activated, preserving its current ownership/history. Legacy firmware without hardware tags retains its old pairing behavior; stronger reset protection applies after tag registration. A tag in ordinary ESP32 NVS does not defend against physical flash extraction/erasure; secure boot/encrypted flash are not enabled by this change.

## Administrator activation (once)

1. In Supabase SQL Editor, apply `remote/migrations/003_camera_setup.sql` after existing schema/002. It is additive and repeatable; no user/media rows are deleted. Keep `CAMERA_SETUP_ENABLED=false` until this succeeds.
2. Create/authorize a Cloudflare account. From `relay/`, run `npm ci`, then `npx wrangler deploy`. This creates the Worker and SQLite Durable Object binding. Review free-plan quotas before deployment; no paid resource was provisioned by development.
3. Generate one fresh random 32-byte hex secret using a secure password manager/tool. Set it as Cloudflare Worker secret `LIVE_RELAY_SECRET` (`npx wrangler secret put LIVE_RELAY_SECRET`) and as the same server-only Vercel environment variable. Set Vercel `LIVE_RELAY_URL` to the exact HTTPS Worker origin, no path/trailing slash, and `CAMERA_SETUP_ENABLED=true`. Do not replace existing Supabase/Meta/encryption credentials. Redeploy the tested preview. Existing functions remain available with live configuration absent; Watch Live stays disabled.
4. Flash the compiled firmware on the prototype. With its physical serial adapter, run PlatformIO Python `tools/setup-card.py COM_PORT`; print the private HTML card in ignored `.private/`. The factory command retrieves only this board's setup card, never over HTTP. For production, ship a preflashed camera with its card. This engineering step is not part of customer setup. Preserve the factory NVS partition when updating; full flash erase invalidates the card/hardware tag.
5. Test outside your LAN before approving production promotion. Neither branch is automatically merged.

## Customer setup

Power camera → join the unique `ROBETIX-xxxxxx` Wi-Fi using its printed 20-character password → open `http://192.168.4.1` (initial captive DNS/probe support is best effort) → create local administrator password → choose STA/home Wi-Fi and enter router password. The setup-card password can be retained; optional hotspot credentials remain editable. Existing installations keep their settings. Join router Wi-Fi/mobile data on the phone; the camera AP itself does not share Internet, even in STA mode.

Sign in at https://robetixvision.vercel.app, select Pair a camera and follow the five steps. Enter the generated code under the local camera's **Connect to my account**. The service URL and trusted roots are built in, with no manual certificate fields in this path. Return to the remote account, refresh cameras, choose Rename and Watch Live. Names synchronize back on heartbeat. Repeat for additional cameras. Local camera functions continue without Internet; remote viewing requires Internet on both ends. Add-to-Home-Screen remains a browser shortcut; no background-video guarantee.

## Bandwidth and cost

Example only: 30 KiB JPEG ×1 FPS is about 105 MiB per viewing hour per direction. Thirty minutes/day is about 1.54 GiB/month camera upload and the same per viewer download; five such cameras about 7.72 GiB/month each direction, plus overhead. Frame sizes/actual throughput vary considerably. Two viewers double relay egress; idle cameras send no footage.

[Cloudflare Durable Object pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) currently lists a free allowance of 100,000 requests/day and 13,000 GB-seconds/day; incoming WebSocket messages count 20:1 as requests. A continuously active 128 MiB object costs about 10,800 GB-seconds/day; five simultaneously active all day exceed that allowance. ACKs also count. Hibernation helps idle connections, not active streaming. Free quota exhaustion interrupts service. Paid rates/Workers bandwidth conditions must be checked before enabling wider use. Vercel/Supabase plan limits and ordinary WhatsApp provider charges still apply; no unlimited/free-always claim.
