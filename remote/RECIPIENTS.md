# WhatsApp recipients: installation and operation

This upgrades the existing backend and dashboard; essential CCTV stays local. Source checkpoint: `checkpoint/pre-whatsapp-recipients` (`dcbf907`). Nothing in this guide claims a production deployment, real Meta delivery or physical ESP32 test has already happened.

## Install once

1. Keep a database backup before applying migrations. For a **new** Supabase project, run `schema.sql`, then `migrations/002_recipients.sql`. For an **existing** project with the original tables, run **only** `migrations/002_recipients.sql`. The migration is transactional and repeatable; it does not drop existing cameras, events or photos. Do not make the tables or storage bucket public.
2. Add `RECIPIENT_ENCRYPTION_KEY` to the dedicated Vercel project's server environment variables: exactly **64 random hexadecimal characters**, representing 32 random bytes. Generate it with a trusted password manager or locally with `node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('hex'))"`. Transfer it directly to Vercel; do not paste it in chat, commit it, put it in frontend variables, or capture it in screenshots. Keep a protected backup. Use different production/test keys. Losing/changing the key without a data migration makes saved contacts unreadable; automated key rotation is not implemented.
3. Keep the existing Supabase and Meta environment values from `.env.example`. `WHATSAPP_DAILY_LIMIT` defaults to **100** provider-message attempts per camera per 24-hour rate window, including tests and failed attempts. It accepts 1–10000. Raising it increases possible charges. The period starts with its first attempt; it is not a midnight calendar quota or a financial spending guarantee.
4. Deploy `remote/` to your **dedicated** Vercel project, initially on its generated HTTPS URL. Root Directory `remote`, framework Other, output `public`, no build command, supported Node 22+ runtime. Keep `NODEJS_HELPERS=0` for raw request streams. `vercel.json` permits up to 60 seconds per function and configures private-browser security headers. There is no permanent worker process. Confirm plan limits in the Vercel dashboard.
5. Keep Supabase public sign-ups disabled. Create the administrator's account in Supabase Authentication; the signed-in camera owner is the administrator of that camera's recipients. This release does not add a separate shared-account administrator/viewer role hierarchy. A different account cannot access these contacts.
6. Run the software checks below, deploy, open `/api/health`, and sign in to the hosted dashboard. Health reports only application/version/running; it does **not** attest that Meta is connected. Configure the camera using its local administrator page and verified HTTPS pairing as described in README.
7. Build/upload the firmware once for the new local dashboard link and removal of its old single-number form. Subsequently, adding/changing recipients requires **no firmware upload, source-code edit, Meta token change, or redeployment**. Recipient management also works with the existing paired camera protocol: old phone/consent settings are imported only once and never remain authoritative afterward.

There is no authenticated Vercel/Supabase/Meta deployment result from this development session. You must sign in to those services, add production secrets, run the migration in your own project and deploy. Do not alter the main `robetix.com` website or portfolio. Add `vision.robetix.com` only to the new project, using the exact DNS records Vercel gives you. No DNS values are invented here.

## Everyday use

On the camera: Advanced Settings → WhatsApp Alerts → **Manage WhatsApp recipients**. This opens the configured hosted HTTPS dashboard, where you sign in separately. Alternatively, open the hosted dashboard, find the camera and press **WhatsApp Alerts**. Remote snapshot viewing can stay Off; it is not required for managing recipients or receiving WhatsApp notifications.

Add up to five people per camera. For each, set a friendly name, a country-code phone number, the explicit consent checkbox, Enabled, Movement alerts, Include a photo and the minimum time between alerts. Phone formats such as `+92 300 1234567` are normalized; local-only numbers and malformed numbers are rejected. The same normalized number cannot be added twice to one camera. Names and numbers are retained as entered data rather than translated.

The administrator must actually obtain permission; ticking a box records the administrator's confirmation, not independent recipient verification. Clear consent when it is withdrawn. Changing the number clears the checkbox in the editor and requires fresh confirmation; the server records a new consent timestamp. Disable preserves settings; Remove deletes the contact. Removal and consent changes stop later submissions, but cannot recall messages already submitted or a provider request already in flight. Honor recipient opt-outs promptly; automated parsing of incoming WhatsApp opt-out messages is not implemented.

**Pause alerts** on the hosted dashboard is a server-side stop and survives camera heartbeats/reboots. Resume to release that stop. The camera's WhatsApp switch must also be On; the backend cannot remotely enable the physical camera's upload switch. The camera's photo switch must be On for newly captured image alerts. Per-recipient preferences can further restrict these master settings. Camera-wide and individual intervals both apply; an explicit test bypasses motion cooldown but has separate throttling and the daily budget.

**Test Notification** on a contact sends only to that saved, enabled, consenting contact. The request cannot supply an arbitrary target number. Text tests need no picture. Image tests use the latest private camera image uploaded within five minutes; the UI says this explicitly. If none exists, use the camera's **Test Notification** for a newly captured frame, or turn off that contact's Include a photo for a text test. The camera's test fans out to eligible recipients; it does not automatically choose just one. The photo's recorded timestamp is used; unsynchronized camera time is shown as unknown. The hosted test marks the camera name with `(Test)` in the existing approved template contract.

Test results report the actual server result. Submitted means a Meta message ID was returned; sent/delivered/read require signed provider receipts. Unknown means the HTTP request may have been accepted and is not automatically resent. With several recipients, partial means at least one succeeded and another failed or is unknown. Each contact shows its own status for its latest retained notification, so one delivery never implies that every recipient received it. Results are refreshed on demand. The camera's heartbeat receives only aggregate state, not contact details.

English/Urdu selection works immediately, with RTL, translated confirmations/errors and browser-local language persistence. Phone numbers use left-to-right layout. Contact data and login credentials are not stored in browser localStorage and are cleared from the recipient UI on sign-out or an authentication-expired response.

## Backend design and security

- `GET /api/recipients?device=UUID&action=list` returns only that authenticated owner's contacts, setup/pause state and latest retained per-recipient delivery outcomes. Every action requires a verified Supabase bearer session and a camera ownership check. Camera credentials cannot manage recipients. Lists and mutations use no-store responses; there is no public contact endpoint or permissive cross-origin access.
- POST to the same endpoint with `action=save`, `remove`, `pause` or `test` requires JSON. Save accepts `id` (null for add), `name`, `phone`, `enabled`, `consent`, `motion`, `photo`, `interval`. Remove accepts `id`; pause accepts `paused`; test accepts `id` and a fresh UUID `request_id`. Do not store bearer tokens in copied examples or URLs. Mutations are rate-limited and bounded.
- `rv_recipients` stores AES-256-GCM encrypted phone numbers and a keyed HMAC for duplicate checks. The encryption key and Meta credentials stay server-side. Names are private database fields. These tables and delivery records have RLS enabled with all anonymous/authenticated direct table access revoked; only the backend service role operates them. Database administrators/server-secret holders remain trusted; this does not protect against a compromised server or authenticated browser.
- Row-locked save/import RPCs bound the list at five, import an opted-in legacy number once, and remove the old phone fields from backend camera configuration. Deleting the last contact cannot recreate it from a heartbeat. The updated firmware stops exposing numbers in its status API and clears its old saved phone after migration acknowledgement. Historical NVS/backup copies are not cryptographically erased; device flash encryption remains outside this release.
- Each event/contact pair has a unique delivery record and atomic sending lease. Version, consent, enablement, motion preference and camera pause are rechecked before submission. An edit can cancel a pending older-version attempt. One private image is uploaded once to Meta and reused for at most five recipients. Request sizes, upstream responses/timeouts and fanout remain bounded. A camera-side timeout may occur before server fanout completes; retries deduplicate the event and later heartbeat/receipt updates show the outcome.
- Failure for one contact does not resend successful contacts. Ambiguous message requests and killed sending workers are marked unknown rather than retried. Daily maintenance reconciles stale attempts and prunes records/photos. It is not a guaranteed low-latency background queue or production availability certification. Changing preferences is not a retry mechanism for an old event.
- Delivery webhook signatures use the existing app-secret HMAC check. Per-recipient receipts cannot downgrade delivered/read to an earlier status. Legacy event receipts remain supported. Provider errors expose numeric error codes and short safe messages, never raw responses containing phone numbers or tokens. Removed contacts leave anonymized event delivery outcomes until ordinary event retention deletes them.

## Meta setup that you must complete

In [Meta Developers](https://developers.facebook.com/), select/create an eligible app with WhatsApp Business Platform. In WhatsApp API setup identify the sender Phone Number ID; the sender ID is not a recipient number. Add/verify allowed test recipients while using Meta's test sender. A dashboard contact alone does **not** add it to Meta's test allowlist.

For production, complete applicable business/sender verification and billing. Issue an appropriate business/system-user token with the required WhatsApp messaging permissions and sender asset access; temporary test tokens expire and are not a production secret-management strategy. Enter the values directly in Vercel's server environment variables. Set a currently supported `META_GRAPH_VERSION` from your Meta account/docs; no guessed version is hardcoded.

Approve an IMAGE-header template and a text-only template matching the existing **two body parameters**: camera name and formatted timestamp (unknown when untrusted). The alert description is fixed approved template text. Configure the exact names and approved language code in `.env.example`. Media upload uses the sender's `/media` endpoint and the template uses its returned media ID, avoiding public camera image URLs. Configure `/api/webhook` with the verify token and app secret; subscribe to message status updates. [Meta's official Postman media-template reference](https://www.postman.com/meta/whatsapp-business-platform/request/2qbotrb/send-message-template-media) was consulted; the developer guide itself returned HTTP 429 during this session. [WhatsApp's policy](https://whatsappbusiness.com/policy/) requires recipient permission and honoring opt-outs.

## Costs checked 2026-10-28

[Vercel pricing](https://vercel.com/pricing) lists Hobby at $0/month and Pro at $20/month, with plan eligibility, resource limits and usage charges applying. [Function-duration documentation](https://vercel.com/docs/functions/configuring-functions/duration) describes configurable limits. Do not assume a personal free plan is suitable for commercial deployment or uninterrupted CCTV alerting.

[Supabase pricing](https://supabase.com/pricing) lists Free with 500 MB database, 1 GB file storage and 5 GB egress; free projects may pause after a week of inactivity. Pro starts at $25/month. Confirm your selected plan, quotas, backups and overage policy. At the listed base prices, Vercel Pro plus Supabase Pro starts around $45/month before messaging, excess usage and taxes; paid plans are not automatically required by this implementation.

[Meta pricing](https://whatsappbusiness.com/products/platform-pricing/) states that delivered messages are charged according to recipient market and message category. The approved template/category and current country rate determine your actual fee; no unverified Pakistan-specific rate or free unlimited allowance is claimed. For example, 20 events/day × 3 eligible contacts × 30 days gives up to 1,800 messages/month before suppression, multiplied by the applicable delivered-message rate. Multiple contacts multiply potential charges. Keep the default attempt budget, set provider budget alerts and review usage. Image storage/egress and hosting usage can also incur costs; check behavior when your free-plan quotas are exhausted.
